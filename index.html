01

Specification

Reliability needs answers you can reproduce, explain and verify

An LLM helps engineers turn plain language into a formal, executable description of expected behavior — a specification. Specifications can combine temporal and spatial patterns, probabilistic methods, anomaly detection and learned system dynamics. At runtime, the specification — not the LLM — evaluates the data, so results are reproducible and verifiable. The specification is also the explanation: every result traces back to the definitions, relationships and data that produced it.

  • Compose simple definitions into complex behaviors
  • Inspect every intermediate definition and relationship
  • Validate specifications before execution
  • Review changes as a normal code diff

Example Prompt

Flag a failed handoff when an unusual change in gripper load is followed by the robot releasing the object before a person takes its weight.

Reviewable specification 
[event.anomaly:load_change]
robot.gripper.force

[event:handoff]
grasped = robot.gripper.holding
early_release = !robot.gripper.holding && !person.hand.holding

[event.sequence.30s:failed_handoff]
handoff.grasped -> load_change -> handoff.early_release

02

Testing, verification and monitoring

From regression testing to real-time monitoring

Use specifications to test recorded runs, catch regressions after every commit, verify edge and tail cases, and continuously monitor live systems. Developers can move quickly without changing what “correct” means between development and operation.

Verification
Checks the system against its specification — not just familiar test scenarios — including edge conditions and low-probability tail cases.
Anomaly detection
Rare failures provide too few examples to learn from. Anomaly detection finds behavior that differs significantly from normal without requiring every failure mode to be known in advance.

Time, spatial, interval and event indexes narrow each search to the relevant data, keeping it fast as datasets grow. Distribution-shift detection identifies when the statistical behavior of data changes over time. Our optimized Kolmogorov–Smirnov test provides a transparent, low-latency alternative to model-heavy approaches.

03

Investigation and response

See what happened. Understand why. Recover safely.

When testing, verification or live monitoring finds a problem, we show exactly what happened, why it was flagged and which expectation it violated. Inspect the evidence in a custom interface generated from the query and specification, or in Foxglove or Rerun. Trigger an automatic or human-approved response, confirm recovery, and preserve what engineers learn in the specification.

  • Link every result to the data and expectation that produced it
  • Generate 2D, 3D and timeline views from queries and specifications
  • Inspect the same evidence in Foxglove or Rerun
  • Run a defined response — stop, enter safe mode, retry or notify an operator
  • Confirm that expected behavior has been restored
